# Session 3 Assignment — Build a RAG App

A RAG pipeline over [docs/DS- Technical Case Study.pdf](docs/DS-%20Technical%20Case%20Study.pdf)
(a real 6-page technical case study document), covering the core
requirement and all four stretch goals.

```
session-3/
  docs/
    DS- Technical Case Study.pdf   <- the knowledge base
  llm_client.py     <- shared: get_client(), call_model(), stream_model(), embed_texts()
  chunking.py        <- load_pdf_pages(), chunk_words()
  vector_store.py     <- in-memory cosine-similarity VectorStore (add/search/save/load)
  ingest.py            <- Ingest -> Chunk -> Embed -> Store (offline indexing)
  rag.py                <- Retrieve -> Generate CLI (online query), + all 4 stretch goals
  test_questions.py      <- 5 test questions with expected-phrase / refusal checks
  test_runner.py           <- runs them, reports PASS/FAIL
  index.json                <- generated by ingest.py (chunk_size=300, overlap=50)
  index_small.json           <- generated for the chunk-size comparison experiment (chunk_size=100, overlap=20)
```

## Vector store: in-memory, not Chroma

Chroma is the "assignment default" but the guidance explicitly allows
"In-memory list -- Learning, under ~5k chunks" for small corpora. This
corpus is 6 chunks from one PDF, nowhere near that ceiling, so
[vector_store.py](vector_store.py) is a plain Python list with brute-force
cosine similarity — zero extra dependencies (no chromadb/onnxruntime),
persisted as a JSON file re-generated by `ingest.py` in about a second.

## Tuning chunk size and k

Ran the same question — *"What happens when a design token like the
primary color is updated?"* — against two indexes built with different
chunk sizes:

| Chunk size | Overlap | Total chunks | Top score | Top 3 sources |
|---|---|---|---|---|
| 300 words | 50 | 6 | **0.529** | p.2, p.5, p.4 |
| 100 words | 20 | 21 | **0.566** | p.2 #1, p.2 #2, p.2 #0 |

Both answered correctly, but the *retrieval* quality clearly differed. At
300 words, each chunk is nearly a whole page, so the one relevant sentence
about token propagation is diluted by everything else on that page —
the model still finds it, but chunks 2 and 3 of the top-3 (pages 5 and 4)
are only loosely related filler, pulled in at a noticeably lower score
(0.390-0.431). At 100 words, the same page got split into 3 focused
pieces, and the top 3 hits were **all 3 sub-chunks of the exact right
section**, at higher confidence. That's the classic chunking "failure
mode" in miniature: chunk too big and irrelevant text dilutes the answer.

For `k`: this corpus only has 6-21 chunks total, so `k=10` in the
`--compare-k` test below just returns "all chunks that exist" rather than
a meaningfully wider net — the well-known k=1-vs-k=10 tradeoff (missing
paragraphs vs. noise flooding the prompt) is real, but only shows up on
corpora with hundreds+ of chunks. With this small a corpus,
`k=3` at `chunk_size=300` was already enough to answer every test question
correctly, and smaller chunks (100 words) would let `k` go a bit higher
without much noise cost, since each chunk carries less.

**Takeaway:** chunk size mattered more than k here — the fix usually goes
back to chunking and k, not "buy a bigger model." Default config landed
on `chunk_size=300, overlap=50, k=3` since
it already passed all 5 test questions cleanly; `index_small.json`
(100/20) is kept as the comparison artifact, not the default.

## Stretch goals

**Compare k=1 vs k=10** (`--compare-k`):

```bash
python rag.py "What happens when a design token is updated?" --compare-k --show-context
```

k=1 retrieved only page 2's chunk; k=10 retrieved all 6 existing chunks
(the corpus doesn't have 10). Both gave the same correct answer here
because the single most relevant chunk already contained the full
answer — a small-corpus version of "k too high floods the prompt with
low-value chunks" (scores dropped to 0.30-0.39 for the extra ones) without
actually breaking the answer.

**JSON output with citations** (`--json`):

```bash
python rag.py "What technology is the design system built on?" --json
```
```json
{"answer": "The design system is built on Angular and Angular Material.", "citations": [{"source": "DS- Technical Case Study.pdf", "page": 1}]}
```

**Streaming** (`--stream`): tokens print incrementally as they arrive via
`llm_client.stream_model()`. Verified live — answer streamed character by
character rather than appearing all at once.

**Re-ranker** (`--rerank`): retrieves top 15 by cosine similarity, then
makes one LLM call asking it to score every candidate 0-10 against the
question (JSON-mode output), and keeps the top k by that score — a
lightweight stand-in for a dedicated cross-encoder re-ranker, since this
environment has no ML re-ranking package installed. Verified
it returns a sensible re-ordering without crashing on this corpus.

```bash
python rag.py "How is the design system distributed?" --rerank
```
