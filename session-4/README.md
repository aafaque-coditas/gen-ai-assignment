## Core requirement

### The 3 required tools ([tools.py](tools.py))

Per the principle that a tool's description is the interface the model
reasons from — one responsibility each, every description says *"Use this
when..."*, units/formats spelled out, structured JSON returns:

| Tool | Responsibility | Real call? |
|---|---|---|
| `calculator` | Arithmetic, via `ast`-based safe evaluator (no `eval`/`exec` — a malformed expression can't run arbitrary Python) | Local, no API |
| `get_movie_info` | Movie metadata by title | Live OMDb API (same endpoint as [../session-2/task-1-sentiment/](../session-2/task-1-sentiment/README.md)) |
| `search_docs` | RAG over the technical case study doc | Wired straight to [../session-3/](../session-3/README.md)'s real `vector_store.py` + `index.json` — no duplicated data, reusing the same code as Session 3 |

A 4th tool, `send_email`, exists purely for the human-in-the-loop stretch
goal below — see that section.

### The ReAct loop ([agent.py](agent.py))

A plain `for` loop against `chat.completions.create(..., tools=...)`,
matching the standard from-scratch ReAct pattern exactly, including
appending the assistant's `tool_calls` message **before** the tool results
(a classic pitfall otherwise) — verified this actually round-trips correctly
against OpenRouter before relying on it:

```python
messages.append(msg)          # assistant turn first
if not msg.tool_calls:
    return msg.content        # done
for tc in msg.tool_calls:
    result = dispatch(tc.function.name, tc.function.arguments, ...)
    messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
```

Every tool call and its observation is logged as `[TOOL]`/`[OBS]`, and each
`[TOOL]` line also carries the model's decision latency.

### Verified: a question needing 2 tools, in the right order

```bash
python agent.py "How many months did the design system project take to deliver, and what is that number times 4?"
```

```
[TOOL] step 1 (2.37s)  search_docs({"query":"design system project timeline"})
[OBS]  {"passages": [{"source": "DS- Technical Case Study.pdf", "page": 1, "score": 0.599, ...

[TOOL] step 2 (1.09s)  calculator({"expression":"6 * 4"})
[OBS]  {"expression": "6 * 4", "result": 24}

Assistant: The design system project took approximately 6 months to deliver. When you multiply that by 4, the result is 24.
```

The model retrieved the "6 months" fact from the doc first, then fed that
number into the calculator itself — it chose the step order at runtime, the
code never told it which tool to call first.

### Verified: `MAX_ITERATIONS` actually stops the loop

Same question, capped at 1 iteration on purpose:

```bash
python agent.py "How many months did the design system project take to deliver, and what is that number times 4?" --max-iterations 1
```

```
[TOOL] step 1 (2.76s)  search_docs({"query":"design system project timeline"})
[OBS]  {"passages": [...]}

>>> Stopped: hit MAX_ITERATIONS (1) without a final answer.
```

It retrieved the doc chunk, then stopped cleanly instead of going on to call
`calculator` — the hard cap actually bites, it isn't just decoration.

## Stretch goal: RAG as a tool (Session 3 meets Session 4)

`search_docs` isn't hard-coded into every query the way [rag.py](../session-3/rag.py)
is — the model decides *whether* it needs the doc at all. The 5-task eval
below includes a general-knowledge question with no tool call at all,
confirming the agent doesn't reach for `search_docs` (or anything else) on a
question the internal doc has nothing to do with — the over-triggering RAG
failure mode ("always retrieve 5 chunks, even for 'what time is it?'"),
avoided.

## Stretch goal: human-in-the-loop gate

`send_email` is the one `DANGEROUS_TOOLS` member. It's simulated (appends to
`outbox.log`, never actually sends anything), but it stands in for any real
destructive/external action, and `agent.py` gates it exactly like a proper
human-in-the-loop implementation should:

**Denied:**
```bash
python agent.py "Send an email to alice@acme.com with subject 'Status' and body 'The design system project is on track.'"
# ...typed 'n' at the prompt...
```
```
[TOOL] step 1 (2.53s)  send_email({"to":"alice@acme.com", ...})
  Agent wants to run send_email(...). Allow? [y/n] n
[OBS]  {"status": "cancelled", "reason": "denied by human-in-the-loop gate"}

Assistant: I cannot send the email at this time due to a restriction...
```
`outbox.log` stayed empty — the tool never actually ran.

**Approved:**
```bash
# ...typed 'y' at the prompt...
```
```
[OBS]  {"status": "sent", "to": "alice@acme.com", "subject": "Status"}
Assistant: The email has been successfully sent to alice@acme.com...
```
```
$ cat outbox.log
TO: alice@acme.com
SUBJECT: Status
BODY: The design system project is on track.
----------------------------------------
```
`--yes` skips the prompt (auto-approves) for scripted/eval runs, where
there's no human at the keyboard to ask.

## Stretch goal: two agents (Planner → Specialist)

[multi_agent.py](multi_agent.py) implements the smallest
orchestrator/specialist split: a **Planner** that can only call
`delegate_to_specialist(step)` — it has none of the real tools itself — and
a **Specialist** that is literally `agent.run_agent()` from the core
assignment, run fresh on one delegated step at a time with no visibility
into the planner's other steps.

```bash
python multi_agent.py "How many months did the design system project take, and what is that number times 4?"
```

```
[PLANNER] step 1 delegates: Determine the duration of the design system project in months.
[TOOL] step 1 (1.34s)  search_docs({"query":"design system project duration"})
[OBS]  {"passages": [...]}
Assistant: The design system project was initially scoped for 12 months but was completed in roughly 6 months...
[PLANNER] specialist returned: ...roughly 6 months...

[PLANNER] step 2 delegates: Calculate 6 months times 4.
[TOOL] step 1 (0.91s)  calculator({"expression":"6 * 4"})
[OBS]  {"expression": "6 * 4", "result": 24}
Assistant: 6 months times 4 equals 24 months.
[PLANNER] specialist returned: 6 months times 4 equals 24 months.

Planner final answer: The design system project took approximately 6 months, and that number times 4 is 24 months.
```

Two independent specialist runs, each with its own tool call and its own
`MAX_ITERATIONS` budget, merged by the planner into one final answer —
neither specialist run ever saw the other's step or the original question.

## Debrief

**Did the agent ever pick the wrong tool? What was the description
problem?** — Not the wrong tool, but a real, reproducible finding one level
down: asking for *"the IMDb rating **and** plot"* of one movie in a single
question made the model issue **two identical parallel `get_movie_info`
calls** instead of one (verified twice, same result both times). The
description didn't say a single call already returns every field, so the
model treated "rating" and "plot" as two separate reasons to call the tool.
Adding one sentence — *"A single call returns ALL available fields at once
... never call this more than once for the same movie"* — fixed it;
re-verified twice after the fix, one call each time, eval still 5/5. Exactly
the point that **the description is the interface**, and an incomplete one
costs a wasted call even when the tool itself is correct.

**When did the loop stop naturally versus hit `MAX_ITERATIONS`?** — Every
real task above stopped naturally in 1–3 iterations (avg 2.0 across the eval
suite). It only hit the cap when deliberately forced to `--max-iterations 1`
on a question that genuinely needed 2 steps — confirming the guard is live,
not just present in the code.

**Where would a human-in-the-loop gate belong in a real product?** — Same
place it landed here: anything external or hard to undo — send/notify
actions, payments, deletes, writes to a system of record. Read-only tools
(`calculator`, `get_movie_info`, `search_docs`) don't need one; the one tool
here with a side effect outside the process (`send_email`) is the one
that's gated, per the "least privilege" and "destructive actions"
principles.
